# ADR-001: Выбор архитектурного стиля — монолит vs микросервисы

**Статус:** Принято
**Дата:** 2026-10-06

## Контекст

Разрабатывается информационная система «Туристическое агентство» для подбора, бронирования и управления турами. Команда состоит из 2 человек, совмещающих несколько ролей (руководитель проекта/разработчик/архитектор/специалист по развёртыванию и тестировщик). Система имеет ограниченную предметную область (туры, пользователи, заявки на бронирование) и не предполагает на старте высоких нагрузок или независимого масштабирования отдельных бизнес-функций. Стек фиксирован: React.js (frontend), Express.js/Node.js (backend), PostgreSQL (СУБД), Docker для развёртывания.

Необходимо выбрать между:
1. **Монолитной архитектурой** — единое backend-приложение на Express.js, обслуживающее все функции (аутентификация, каталог туров, заявки) через общий REST API и одну базу данных.
2. **Микросервисной архитектурой** — разделение функциональности на независимые сервисы (например, сервис пользователей, сервис туров, сервис заявок), каждый со своей базой данных и отдельным развёртыванием.

## Решение

Принято решение использовать **монолитную архитектуру**: единое Express.js-приложение с модульной внутренней структурой (разделение на `controllers`, `services`, `models`, `routes` по предметным областям) и единой базой данных PostgreSQL.

Обоснование:
- Команда из 2 человек не обладает ресурсами для сопровождения инфраструктурной сложности микросервисов (service discovery, межсервисная коммуникация, распределённые транзакции, множественные CI/CD-пайплайны).
- Предметная область на данном этапе невелика (3 роли, 5-6 сущностей), жёсткой необходимости в независимом масштабировании отдельных модулей нет.
- Монолит с чёткой модульной структурой внутри (по контроллерам и сервисам) упрощает отладку, тестирование и развёртывание через один `docker-compose.yml`, что соответствует срокам и ресурсам учебного проекта.
- Модульная организация кода внутри монолита позволяет при необходимости в будущем выделить отдельные модули (например, модуль заявок) в самостоятельный сервис без полного переписывания системы.

## Последствия

**Положительные:**
- Простое развёртывание: один контейнер backend, один контейнер frontend, один контейнер БД — соответствует ресурсам арендованного сервера и навыкам команды.
- Упрощённая отладка — все запросы проходят через единый процесс, нет необходимости трассировать запросы между сервисами.
- Меньше накладных расходов на инфраструктуру (нет необходимости в API Gateway, service mesh, дополнительных очередях сообщений).
- Быстрее реализуются сквозные операции (например, транзакционное обновление доступности мест при одобрении заявки — выполняется в одной БД, в одной транзакции).

**Отрицательные / риски:**
- При существенном росте нагрузки масштабирование возможно только горизонтально для всего приложения целиком (нельзя масштабировать только модуль бронирования отдельно от каталога).
- Любое изменение в одном модуле требует пересборки и повторного развёртывания всего приложения.
- Высокая связанность кода при отсутствии дисциплины в структуре модулей может затруднить сопровождение при росте команды.

**Компенсирующие меры:** модульная структура кода (разделение по доменам внутри `backend/src`) закладывается заранее, чтобы облегчить возможный переход к микросервисам при будущем росте нагрузки или команды.
